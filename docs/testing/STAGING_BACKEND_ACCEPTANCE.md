# ThePlugOS staging backend acceptance protocol

- **Status:** Protocol ready; remote execution pending
- **Date:** 12 October 2026
- **Release status:** HOLD until every mandatory live gate has measured evidence
- **Architecture:** ADR-007, ADR-008, ADR-009, ADR-010, ADR-012, ADR-015, ADR-016, ADR-019, ADR-020
- **Source gates:** R016, R017, R019, R024, R025, R029, R030

This protocol is the current acceptance path for an isolated Supabase staging-equivalent environment. It does not authorize production mutation and does not convert source/fixture/CI evidence into live backend or physical-device evidence.

## 1. Environment boundary

The rehearsal target must be a fresh, authorized ThePlugOS staging-equivalent project.

The following targets are prohibited:

- production `iwbbwcaylpulcpvbfkdx`;
- preserved contaminated legacy staging `dpqtgfxovmiwzkiuzoya`; and
- any Supabase project belonging to another application merely because it is available to the connected account.

If no authorized isolated ThePlugOS staging project is available, all remote cases in this protocol are **BLOCKED**. They are not failed and they are not passed.

## 2. Required secure inputs

The operator must provide these only through the secure execution environment. Never commit or paste their values into evidence:

- `SUPABASE_ACCESS_TOKEN`;
- `THEPLUGOS_STAGING_DATABASE_URL` for the exact staging project;
- `HUB_AUTHORIZATION_ISSUER_PRIVATE_JWK_JSON`;
- `HUB_RATE_LIMIT_PEPPER`;
- database passwords or pooler credentials; and
- any platform/service secret generated by Supabase.

The following non-secret values must be recorded with the acceptance evidence:

- staging project ref;
- source commit;
- GitHub Actions run for that source commit;
- `HUB_AUTHORIZATION_ISSUER_KEY_ID`;
- issuer public-key fingerprint only, not the private JWK;
- owner portal HTTPS origin;
- Function deployment versions/identifiers;
- schema verification timestamp; and
- Android candidate/public issuer-map hash if hardware testing proceeds.

## 3. Staging schema path

Do **not** use `supabase db push` for this rehearsal. The canonical R001A source filename is intentionally preserved as `001a_retire_unsupported_legacy_staff_pins.sql`, which does not match current Supabase CLI numeric migration discovery. Production also has a separately recorded remote migration ledger.

Use the guarded rehearsal path:

```text
scripts/deploy-hub-cloud.sh --rehearse-staging
```

The helper invokes `scripts/apply-staging-schema.mjs`, which must apply the following exact order to an empty staging target:

`001 -> 001A -> 002 -> 003 -> 004 -> 005 -> 006 -> 007 -> 008 -> 009 -> 010 -> 011 -> 012 -> 013 -> 014 -> 015`

A non-empty canonical ThePlugOS target is an immediate **STOP**. Restore/create a clean staging target instead of replaying the sequence over unknown state.

## 6. Gate B — ordered schema 001–015

| ID | Test | Required measured result |
| --- | --- | --- |
| B01 | R001 baseline | Core business/branch/staff/catalog schema applies successfully. |
| B02 | R001A explicit application | `001a_retire_unsupported_legacy_staff_pins.sql` executes between R001 and R002; it is not skipped by CLI discovery. |
| B03 | R002–R013 authority baseline | Every ordered source migration commits successfully with no partial failed transaction. |
| B04 | R014 terminal session authority | R014 applies after R013 and exposes the required terminal staff-session RPCs/challenge table. |
| B05 | R015 owner RLS hardening | R015 applies last and retires the broad member write policies. |
| B06 | Post-apply verification | Applicator reports all required R014/R015 verification flags true. |

Any migration failure is **FAIL / STOP**. Do not hand-edit the staging schema to force continuation.

## 7. Gate C — live RLS and owner control-plane authorization

Use real Supabase Auth identities in staging. Source inspection alone does not pass this gate.

| ID | Test | Required measured result |
| --- | --- | --- |
| C01 | Owner staff INSERT | Authenticated business owner can create a branch-bound Cashier/Kitchen/Manager directory profile. |
| C02 | Non-owner staff INSERT | Authenticated non-owner business member is denied. |
| C03 | Cross-business/branch staff INSERT | Owner cannot create a staff row for another business or an inactive/mismatched branch. |
| C04 | Staff UPDATE denial | Browser authenticated owner/member cannot directly update role/status because no authenticated RLS UPDATE policy exists. |
| C05 | Owner catalog INSERT/UPDATE | Owner can create/update catalog metadata inside valid business/branch scope. |
| C06 | Non-owner catalog write | Authenticated non-owner member is denied catalog INSERT/UPDATE. |
| C07 | Cross-scope catalog write | Owner cannot move/write catalog metadata into another business or mismatched branch. |
| C08 | Physical stock protection | Browser owner path does not write physical stock quantity as a substitute for native inventory commands. |

Capture only row IDs, policy outcomes and redacted error classes; never capture tokens.

## 8. Gate D — Edge Function deployment and authentication modes

All seven Functions must be deployed only after Gate B passes.

| ID | Function | Required platform/auth boundary |
| --- | --- | --- |
| D01 | `hub-owner-enrollment` | `verify_jwt=true`; valid Supabase owner JWT plus owner/business/branch authorization required. |
| D02 | `hub-enrollment` | `verify_jwt=false`; native signed proof only; no browser CORS. |
| D03 | `hub-staff-session` | `verify_jwt=false`; native signed Hub proof only; no browser CORS. |
| D04 | `hub-staff-credential-reset` | `verify_jwt=false`; owner-authorized reset + native Hub proof; no browser CORS. |
| D05 | `hub-sync` | `verify_jwt=false`; signed Hub request and service RPC validation; no browser CORS. |
| D06 | `hub-terminal-enrollment` | `verify_jwt=false`; terminal-key proof + owner-issued admission code; no browser CORS. |
| D07 | `hub-terminal-staff-session` | `verify_jwt=false`; terminal key/admission/Hub/staff/PIN challenge proof; no browser CORS. |

For every custom-proof receiver, an unsigned/malformed request must be rejected before any durable authority mutation.

## 9. Gate E — terminal staff-session receiver

This gate requires staging R014 plus a legitimately enrolled Hub and admitted terminal.

| ID | Test | Required measured result |
| --- | --- | --- |
| E01 | Begin session | Valid admitted terminal/Hub/staff request creates only a short-lived challenge bound to the supplied identities. |
| E02 | Wrong/stale challenge | Wrong request ID, challenge ID, nonce or expired challenge fails closed. |
| E03 | Terminal proof | Correct terminal Keystore signature is accepted; incorrect key/signature is rejected. |
| E04 | PIN verification | Correct native PIN completes service-side verification; wrong PIN follows lockout/throttle behavior without exposing credential facts. |
| E05 | Role binding | Requested/issued role must equal the admitted terminal role and staff role. |
| E06 | Assertion binding | Signed assertion contains and validates exact terminal device, Hub, branch, business, staff, role and validity window. |
| E07 | Same-staff supersession | New session retires old same-terminal and same-staff Hub sessions as R014 requires. |
| E08 | No browser credential surface | PIN/session assertion/private material is absent from browser storage, owner portal responses and public logs. |

## 10. Gate F — Hub sync and durable acknowledgement

| ID | Test | Required measured result |
| --- | --- | --- |
| F01 | Signed batch | Valid signed Hub batch accepted only for current Hub/business/branch authority. |
| F02 | Malformed batch | Invalid IDs, payloads, sequences or unsupported action families fail before durable mutation. |
| F03 | Contiguous grouping | Receiver processes only valid contiguous action-family groups in sequence. |
| F04 | Exact acknowledgement | Each group returns exactly the IDs expected for that group; duplicate/cross-group/missing IDs fail closed. |
| F05 | Exact retry | Repeating the same durable command/event produces one business effect and stable acknowledgement semantics. |
| F06 | Cloud outage | Local outbox remains pending while Function/cloud is unavailable. |
| F07 | Restart recovery | Hub restart retains pending outbox state and later drains it without duplicate business effect. |
| F08 | Branch isolation | Cross-business or cross-branch payload cannot create or acknowledge durable effects. |

## 11. Gate G — owner endpoint and secret configuration

| ID | Test | Required measured result |
| --- | --- | --- |
| G01 | Exact origin | Owner browser Function accepts only configured `HUB_OWNER_PORTAL_ORIGIN`; wildcard/path variants are rejected. |
| G02 | Owner identity | Non-owner authenticated user cannot mint owner enrollment authority. |
| G03 | Issuer pair | Staging private JWK and Android/public SPKI are a verified matching P-256 pair before deployment. |
| G04 | Secret isolation | Private issuer key, pepper, DB password and service key are absent from source, browser variables, APK resources and evidence. |
| G05 | TTL bounds | Authorization bundle TTL remains within the source-guarded 15–720 minute window. |

## 12. Gate H — handoff to physical multi-device acceptance

Backend acceptance is not complete product release. Once Gates A–G pass, continue with `docs/testing/PHYSICAL_MULTI_DEVICE_TERMINAL_ACCEPTANCE.md` using a candidate built with the matching staging public issuer-key map and staging Functions base URL.

Do not convert a staging backend PASS into production approval until physical tests have measured:

- Hub + independent terminals;
- native PIN activation/recovery;
- cross-device same-staff supersession;
- LAN mDNS / Wi-Fi Direct / BLE proximity boundaries;
- TLS certificate-pin rejection and fresh challenge proof;
- link-loss safe-stop;
- restart/exact-retry behavior; and
- durable cloud acknowledgement.

## 13. Result rule

- Any mandatory **FAIL** keeps release status HOLD and requires correction plus a fresh acceptance run.
- Any mandatory **BLOCKED** keeps release status HOLD; do not infer PASS from source or fixtures.
- Only direct measured evidence tied to exact project, source commit and deployment identifiers can close a live gate.
